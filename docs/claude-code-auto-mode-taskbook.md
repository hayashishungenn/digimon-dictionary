## 二、当前审查结论与基线

### 2.1 产品结论

当前系统已经具备一个合理图鉴 MVP 的主要骨架，以下能力可以使用：

- 三语名称搜索、别名搜索、部分匹配搜索。
- 官方/扩展集、等级、属性、领域、组织、X-Antibody 等组合筛选。
- 列表、详情、技能、别名、组织、关联形态、首次登场字段、来源信息展示。
- 有向多对多进化关系模型，支持简单模式和图模式。
- FastAPI、SvelteKit、SQLite、数据抓取/标准化/匹配/合并/验证的基本链路。
- 基础 lint、Python 测试、前端检查、前端单元测试、构建和 fixture E2E 可以通过。

但尚未达到初版任务书的最终验收标准，不能称为“完整、可持续更新、发布就绪”的全图鉴，主要原因是：真实数据覆盖仍不完整，真实数据下的进化图会急剧膨胀，抽样验证命令失败，图片缩略图与首次登场 UI 存在缺口，增量同步的失败安全和审计链仍不够可靠。

## 三、完成定义

全部 P0/P1 任务完成后，系统至少应满足：

1. 首屏列表、搜索、详情、筛选、组织页和进化图在真实数据库上可操作，不因真实关系规模卡死或返回不可渲染的无界数据。
2. 进化图默认轻量展示，depth 1–3 有明确上限、截断标识和加载状态，服务端拒绝超出范围的请求。
3. 首次登场、主图、缩略图、占位图和版权/来源状态在数据存在、数据缺失、下载失败三种情况下都能正确表达。
4. 抽样验证命令能以确定性方式运行并返回可审计结果；固定 16 条样本全部通过，随机 50 条样本不允许通过修改断言来掩盖真实数据问题。
5. 同步流程不会在未验证、原始数据不完整、状态保存失败或图片阶段失败时静默发布不可审计的数据集。
6. 每个关键字段和关系都能追溯到来源、URL、抓取时间或明确的缺失/冲突状态。
7. 真实数据库 smoke test、API 集成测试、前端测试和至少一套真实数据 E2E/手工验证均完成；fixture 测试只能作为补充。
8. 质量报告、交付报告、README 和任务状态中的数量、快照日期、已知缺失与实际数据库一致。

## P0-1：修复真实数据下的进化图规模、性能和可用性

### 目标

让进化关系满足初版任务书“默认 depth=1、可选 depth=2/3、不能绘制全网”的要求。当前真实数据库 depth=3 约 33 秒且返回 1506 个节点、18051 条边，已经构成实际可用性问题。

### 预期改动范围

- API 参数和错误处理：apps/api/main.py
- 图查询、去重、遍历和分页/截断：apps/api/queries.py
- 图组件和加载/截断提示：apps/web/src/lib/components/EvolutionGraph.svelte
- 详情页的 depth 切换、错误状态、节点计数：apps/web/src/routes/digimon/[slug]/+page.svelte
- API 单元/集成测试：tests/ 下与 evolution 相关测试
- 前端 E2E：apps/web/tests/ 或现有 Playwright spec

### 执行要求

1. 服务端只接受 depth 1、2、3；超出范围返回明确的 4xx，不允许当前的 depth=4 继续放大查询。
2. 默认仍使用 depth=1；depth=2/3 必须显式请求。
3. 增加节点/边预算和 truncated、实际节点数、实际边数等可解释状态；达到预算时返回可用的部分图，而不是超时、白屏或静默丢关系。
4. 优化查询和去重算法，避免对边集合做 O(E²) 级别的重复扫描；必要时使用稳定排序保证结果可复现。
5. 前端展示加载中、空图、截断、请求失败和节点过多提示；用户仍可点击节点进入详情页。
6. 为真实 data/digidex.sqlite 增加 smoke test，不能只使用 7 条实体的 fixture。

### 验收标准

- depth=0、depth=4 和非法字符串均返回稳定、可解释的参数错误。
- depth=1 首次打开不出现明显卡顿；depth=2/3 在真实数据库上有硬性资源上限，不返回不可渲染的全量图。
- 响应包含截断状态时，UI 明确告知用户还有未展示的关系，并允许回到较小深度。
- API 结果中的节点/边不重复，根节点始终存在，方向和边类型不被破坏。
- 新增测试覆盖：环、重复边、孤立节点、超预算、未知 slug、真实规模数据。
- 验收记录必须包含真实 DB 的耗时、节点数、边数和浏览器操作结果。

### 依赖关系

- 依赖 P0-0 的真实规模基线。
- P1-3 的真实 E2E 依赖本任务完成。

### 潜在风险和注意事项

- 简单地把 depth 上限改成 1 不是完整修复；必须保留 depth=2/3 的可用路径。
- 不能为了性能静默删除有来源的边；截断必须可见并可审计。
- 图数据允许环，环不能被 validator 当作错误，也不能导致无限遍历。

## P1-1：重构增量同步的失败安全、原始快照和恢复能力

### 目标

保证抓取失败、校验失败、状态保存失败、图片阶段失败、源集合变化或进程中断时，不会静默发布不完整数据库，并且可以从 checkpoint 恢复和审计。

### 预期改动范围

- 同步编排、发布门禁、checkpoint 和状态：scripts/sync_data.py
- 原始快照写入与错误处理：pipeline/sources/base.py、pipeline/core/ 相关模块
- 同步历史表、运行 ID 和迁移：pipeline/core/schema.py
- 相关测试：tests/integration/、tests/unit/
- 文档：docs/sources.md、README.md

### 执行要求

1. 原始响应先写入临时文件，校验成功后原子替换；写失败、截断、内容类型错误不得被标记为完整。
2. --skip-validation 只能用于诊断或开发，不得使未验证 candidate 通过 publish gate。
3. checkpoint、状态文件、数据库 publish、图片结果保存均必须检查返回值；失败要停止发布或明确标记为不可发布。
4. source 集合变更必须同时识别新增、删除和参数变化，不能只检测删除源。
5. source_sync 保留每次运行记录和 run_id，不能只用 source 主键覆盖历史；至少能查询某个版本由哪些源、何时、以什么状态生成。
6. 完成中断恢复测试：抓取中断、raw 写失败、验证失败、publish 后状态保存失败、图片阶段失败。

### 验收标准

- 任一源失败或 raw 不完整时，最终数据库和“最新成功版本”不被替换。
- 任何未通过验证的 candidate 都不能被标记为 published/ready。
- 中断后重新运行可以从 checkpoint 继续，或明确从头开始且不会混入上一轮半成品。
- source_sync 能保留至少两次运行历史并可追溯每次运行状态、源集合、错误和快照。
- 新增/删除来源的增量检测有单元测试；关键失败注入测试退出码非零且数据库状态可解释。

### 依赖关系

- 依赖 P0-0；发布门禁部分依赖 P0-2。
- P1-2、P2-1 的最终持续更新验收依赖本任务。

### 潜在风险和注意事项

- 不要为了实现原子发布而删除旧的可用数据库；应采用 candidate + manifest + 原子切换或现有等价方案。
- SQLite WAL、文件锁、跨 Windows/CI 文件替换行为需要在当前运行环境真实验证。

- 详情页来源表和名称起源显示：apps/web/src/routes/digimon/[slug]/+page.svelte
- 测试：tests/、apps/web/tests/

### 执行要求

1. 对嵌套模板、链接、HTML、换行、日文/英文/中文混排建立最小可靠清洗器；无法安全解析时保留原文并标记待人工复核，不要静默误删。
2. provenance 至少保留 source、source_url、retrieved_at、字段/记录标识和抓取运行 ID。
3. 同一字段多源冲突不得通过 INSERT OR IGNORE 静默吞掉；必须保存当前值、候选值、来源、解决状态和复核入口。
4. 进化边和关系不能硬编码成单一官方来源；每条边/关系要能追溯其实际来源。
5. 内容哈希必须覆盖会影响最终实体的规范化字段，而不是只哈希 extra。
6. 详情页来源展示应区分“已验证”“有来源但未人工确认”“冲突”“缺失”。

### 验收标准

- 名称起源、简介、技能、进化边、组织关系的 API 响应都能返回有效来源或明确缺失状态。
- 页面不再显示未处理的 Wikitext 模板；新增清洗测试覆盖嵌套模板和保留原文场景。
- 相同输入重复同步不会产生无界重复 provenance/conflict 记录；内容变化能触发更新。
- 冲突报告包含数量、样本、来源和处理状态，且未解决冲突不会被伪装成已确认数据。

### 依赖关系

- 依赖 P1-1 的运行 ID/快照语义；部分字段覆盖问题依赖 P0-2。

### 潜在风险和注意事项

- “清洁文本”不能等同于“改写文本”；只做结构清洗，不改变事实语义。
- 中文名必须保留 official、official_game、official_anime、community、transliteration、unverified 等来源状态，不能把社区译名冒充官方名。

## P1-3：补齐真实数据库 API、浏览器和移动布局验收

### 目标

把现有 fixture 测试和真实数据验证分开，确保用户实际打开 1736 条数据时的搜索、筛选、详情、进化图、组织页和来源展示都可用。

### 预期改动范围

- API 集成测试：tests/
- 页面组件：仅修复真实验收发现的问题，优先 apps/web/src/routes/ 和 apps/web/src/lib/components/
- CI 配置：.github/workflows/（如已有配置）

### 执行要求

1. 保留小型 fixture E2E，用于快速验证；另加真实 DB smoke/E2E profile，明确设置 DIGIDEX_DB=data/digidex.sqlite 或等价配置。
2. 至少覆盖：中文、繁体中文、英文、日文、别名和部分匹配；组合筛选；Agumon 详情；技能；组织页；来源表；首次登场日期；图片缺失占位；depth 1/2/3 和截断状态。

### 验收标准

- fixture E2E 和真实 DB smoke/E2E 都能通过，且测试报告明确标识数据来源。
- 真实数据下至少一个三语实体和一个扩展集实体完整走通列表→详情→技能/来源→进化→返回列表链路。

- CI 运行不会依赖未提交的本地 data/images/；缺失图片必须通过占位状态稳定测试。

### 依赖关系

- 依赖 P0-1、P0-3；P1-2 的 API 来源变化完成后重跑。

### 潜在风险和注意事项

- 真实 DB E2E 可能比 fixture 慢，必须设置合理超时并报告耗时；不能无限加 timeout 掩盖性能问题。
- 测试不得修改用户本地数据库；如需测试数据，使用只读真实 DB 或临时副本，并明确其生命周期。
